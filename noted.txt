WHAT IT CHANGES
---------------
Settings are split per property segment. Every key except `currency` and
`dormitory` now carries one value per segment, and BOTH are required -- there
is no shared fallback, so a segment can never quietly inherit the other's
price.

  new  segment_settings (key, segment, value, updated_at, updated_by)
       Authoritative. PK (key, segment), FK key -> settings(key).
  new  segment_settings_history      audit trail, mirrors settings_history (0010)
  new  settings.is_segment_scoped    boolean, false only for currency + dormitory

  new  segment_setting_numeric(text, property_segment)
  new  payment_grace_days(property_segment)
  new  default_monthly_rent(property_segment)
  new  default_deposit(property_segment)

  changed  payment_grace_days()      -> raising stub
  changed  default_monthly_rent()    -> raising stub
  changed  default_deposit()         -> raising stub
  changed  v_room_board                       repointed at the segment forms
  changed  recalc_invoice(uuid)               repointed
  changed  mark_overdue_invoices()            repointed
  changed  report_finance_summary             repointed (balances CTE gains a rooms join)
  changed  report_finance_summary_by_segment  repointed

  triggers  segment_settings_scoped_only      rejects a value for a non-scoped key
            settings_scoped_value_frozen      rejects UPDATE of settings.value
                                              for a scoped key
            settings_seed_segments            auto-creates both segment rows
                                              for a newly inserted setting
            segment_settings_set_updated_at
            on_segment_settings_value_changed writes the history row

Backfilled from current values, so nothing changes price on the day it runs.

THREE DELIBERATE DESIGN DECISIONS, so they are not "fixed" later by mistake
---------------------------------------------------------------------------
- settings.value is FROZEN for scoped keys. `update settings set value = ...`
  raises rather than silently doing nothing. One source of truth for a price.
- The no-argument SQL functions are kept as RAISING STUBS rather than dropped,
  so any caller that was missed fails loudly instead of reading a frozen value
  and billing the wrong segment.
- A missing (key, segment) row RAISES. Billing 0 THB silently is far worse than
  failing. Both rows stay present via the backfill, settings_seed_segments, and
  the absence of any delete grant or policy on segment_settings.

5. STANDING NOTES
====================================================================

- Migrations are append-only. Never edit an applied file; add a new numbered
  one.
- `npm run db:push` is the intended path and records what it applied in
  schema_migrations. Applying by hand in the SQL editor does NOT, so always
  add the bookkeeping insert or the next db:push will try again.
- After any schema change, regenerate or hand-update src/types/database.ts.
  Row shapes must be `type`, not `interface`, and an append-only table's
  Update must use the NoWrites helper -- break either and every query
  silently degrades to `never`.
- src/lib/reporting/exclusion.test.ts is the regression test for the
  is_test invariant. If you touch schema, seeds or reporting, it must pass.
